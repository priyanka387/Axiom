# ADR 0002: Organization and User Domain Model

## Status

Accepted

## Context

Axiom is an enterprise AI workforce platform.

Enterprise data and agent activity must be isolated by organization. The
organization therefore acts as the initial tenant boundary for the domain
model.

Axiom also needs an internal representation of users without coupling the
core domain directly to a specific authentication or identity provider.

## Decision

### Organization

`Organization` represents an Axiom tenant.

Each organization has:

- UUID identity
- human-readable name
- globally unique slug
- creation timestamp
- update timestamp

Organization slugs are stored in lowercase.

### User

`User` represents an organization-scoped principal.

Each user has:

- UUID identity
- organization foreign key
- email
- display name
- lifecycle status
- optional external identity subject
- creation timestamp
- update timestamp

User email addresses are unique within an organization and stored in
lowercase.

Supported lifecycle states are:

- `active`
- `suspended`
- `deactivated`

### Tenant isolation

Every user belongs to exactly one organization.

The organization foreign key uses database-level cascade deletion so that
users cannot remain orphaned after an organization is removed.

Future tenant-scoped entities should either reference `Organization`
directly or derive their tenant boundary through an explicitly auditable
parent relationship.

### Identity provider independence

The domain model does not depend on Keycloak, Auth0, Cognito, or another
identity provider.

The optional `external_subject` field allows an authentication layer to map
an external identity to an Axiom user.

This keeps authentication concerns outside the core domain model.

### UUIDs

UUIDs are generated by the application rather than requiring PostgreSQL
extensions.

This keeps the initial database portable and simplifies local development.

### Timestamps

Creation and update timestamps use timezone-aware database columns.

Creation timestamps are generated by PostgreSQL.

Update timestamps are maintained by the SQLAlchemy model layer.

## Consequences

### Positive

- Establishes the initial enterprise tenant boundary.
- Prevents duplicate user emails within the same organization.
- Provides explicit user lifecycle states.
- Keeps authentication provider choices independent from the domain model.
- Provides a foundation for future agent, tool, workflow, policy, approval,
  and audit entities.

### Negative

- Tenant isolation must be consistently enforced when additional domain
  entities are introduced.
- Authentication and authorization are not solved by this model alone.
- More sophisticated enterprise identity features will be introduced in a
  later security milestone.

## Future work

Later milestones will introduce:

- roles and permissions
- authentication integration
- organization membership controls
- agent ownership
- tool authorization
- policy enforcement
- audit events
- approval workflows
